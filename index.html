CASE 01
TEST AUTOMATION

Turning UI failures into testable evidence

Playwright TypeScript UI Testing

While working with network analytics UI automation, I worked with workflows where the expected data existed but the test could still fail because the locator, rendered text, card state or selected UI element did not match what the test expected.

Problem A test could fail even when the application contained the expected information because the automation was not targeting the correct UI element or state.
Investigation I inspected the page structure, visible text, selectors, card state and actual data presented by the workflow before changing the test.
Validation I adjusted the test logic and helper usage so validation focused on the intended application data instead of relying on an incorrect element.
Lesson A failed automated test does not automatically mean the application is wrong. The test itself also needs to be investigated.

CASE 02
DATA VALIDATION

Validating IPDR report data

IPDR Reports Validation

I worked with IPDR-related UI workflows where a report had to be checked against expected query results and required fields. The important part was not only whether a report was generated, but whether the generated output contained the information that the validation expected.

Problem Report generation could complete while the output still needed to be checked carefully for expected fields and values.
Investigation I compared the generated report structure with the expected fields and treated missing or unexpected data as validation evidence.
Validation I built checks around the report content so automation could identify whether the expected report structure was actually present.
Lesson A successful workflow and a correct result are two different things. Data validation needs to verify the actual output.

CASE 03
SECURITY VALIDATION

When security hardening affects application behaviour

CSP Cookies Nginx

Security hardening cannot be treated independently from application functionality. During security validation work, I encountered situations where security-related configuration changes affected application behaviour and needed to be investigated carefully.

Problem A stricter security configuration could affect browser resources or application behaviour, including UI or login-related functionality.
Investigation I compared behaviour before and after the security configuration change and looked at which part of the application behaviour was affected.
Validation The security change had to be considered together with application functionality so security validation did not become a blind configuration exercise.
Lesson Security controls have to be validated in the context of the application. Their effect needs to be understood and tested.
Back to Experience →
CASE 04
DETECTION ENGINEERING

Building and validating Suricata detection rules

Suricata MITRE ATT&CK IDS / IPS

Through my security projects and lab work, I worked with Suricata rules mapped to selected MITRE ATT&CK techniques. The goal was to understand how controlled security activity appears to a detection system and how rules can be validated.

Problem A detection rule needs to identify the intended activity without simply assuming that the presence of traffic means the detection is correct.
Investigation I used controlled lab activity and examined Suricata output to understand whether the expected detection behaviour occurred.
Validation Rules were checked against the intended technique and observed alert behaviour rather than treating a rule file as complete simply because it loaded.
Lesson Detection engineering is not only writing rules. It also requires controlled testing and examination of the evidence produced by the detection system.

Python Scapy Suricata Linux
